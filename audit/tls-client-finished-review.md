# TLS 1.3 client Finished handling

Date: 2026-11-24

## Static path

Pinned current upstream source:
`FileSherlock/k15@cb9f76a5a100c418bfcaeddcd4f137d30ab489d2`.

The server's handshake routine in `src/tls.asm` builds and seals its
ServerHello/EncryptedExtensions/Certificate/CertificateVerify/Finished flight,
then derives the client and server application traffic secrets. It advances
the connection to the application stage without a subsequent client-Finished
verification step.

The inbound `record` routine in `src/request.asm` is explicit about its
scope: it handles an application-data record (outer content type 23), decrypts
with the client application traffic key at `C_KIV+44`, and checks the AEAD
tag. It does not verify a client Finished under the client handshake traffic
secret. Non-application records, including the client's handshake-key Finished,
are ignored by this routine.

Consequently, the server can accept an application-data record authenticated
with the client application traffic key even when it has not received the
client Finished. This is a TLS 1.3 handshake-state/conformance weakness. It
does not show that an off-path attacker can derive the application traffic
key, forge application data, recover the server's private key, or bypass a
client-authentication policy (none is exercised by this test).

## Existing dynamic evidence

The existing `test_tls_record_rejection.py` completes a TLS 1.3 handshake
locally with OpenSSL, corrupts the client's encrypted Finished record, then
sends a valid application-data record generated by the same client. The frozen
bounty, first upstream fix and current upstream have all returned HTTP in the
recorded differential runs:

- [frozen bounty and first fix](https://github.com/miSultanato/k15/actions/runs/45394628025)
- [current upstream](https://github.com/miSultanato/k15/actions/runs/45401470623)

This proves continued application processing after the corrupted record, but
the original test does not isolate omission from corruption.

## New omission control

A new `test_omitted_client_finished` case now deliberately discards the
client's handshake-key Finished bytes from the OpenSSL output BIO and sends
only the first application-data record over the established TCP socket. The
client still derives its application traffic keys locally from the completed
server flight. The test requires an HTTP response in `expect` mode.

The differential workflow invokes this test script for the frozen bounty and
both upstream revisions. The push-triggered [run 45482705312](https://github.com/miSultanato/k15/actions/runs/45482705312)
completed successfully (job 138759780549). Its logs show:

- frozen bounty, expect mode: omitted Finished → HTTP response; corrupted Finished → HTTP response; bad AEAD record ignored and valid same-sequence record processed;
- first upstream fix and current upstream, observe mode: omitted Finished and corrupted Finished both followed by HTTP responses; bad AEAD record ignored and valid same-sequence record processed.

Thus the omission control is no longer pending. The run uses synthetic QEMU images on an ephemeral GitHub-hosted runner; it is not a local NEO run and does not contact production.

## Interpretation

This is a missing client handshake-confirmation check, not a Finished-MAC
forgery. A client that knows the shared secret can derive application traffic
keys and send a valid application record without first sending Finished. The
test does not show that a party lacking those keys can do the same.

All validation remains local to synthetic QEMU images and generated
credentials. No production service or credential is involved.

## Runtime result and limits

The omission control confirms that the server accepts a valid application
record before client Finished on all three revisions. The same run also
confirms that a corrupted Finished is not a gate before application processing,
while a bad application AEAD record itself is ignored and a valid same-sequence
record is processed. This is a protocol state/handshake-confirmation weakness
shared by the tested versions. The application record remains AEAD-authenticated
under the client application traffic key; the result does not imply an attacker
without the shared secret can inject data. No client-certificate policy, client
identity, or authorization boundary was tested.
