# Public cross-curve DLEQ proof review

Date: 2026-11-24

Target: `tools/bounty.py` and `bounty.proof` on frozen branch
`ab93479ebc7c85274c722b16897148286d1cfca3`.

## Purpose

The public proof establishes that the P-256 public key in the TLS certificate
and the secp256k1 public key behind the published Bitcoin address use the same
integer private scalar. It is not intended to reveal that scalar.

The proof is public, offline-verifiable and separate from the TLS handshake.
Its randomizers are generated by Python's `os.urandom`; this is not the
server's RDRAND path and does not reuse the server's ECDSA nonces.

## Serialized contents

The binary proof is 41,172 bytes:

| Field | Bytes | Meaning |
|---|---:|---|
| Version + flip | 2 | Format version and high-scalar normalization bit |
| Q1 + Q2 | 66 | Compressed P-256 and secp256k1 public keys |
| 128 pairs of commitments | 8,448 | One Pedersen commitment per base-4 digit, on each curve |
| Initial challenge | 16 | 128-bit Borromean challenge |
| 510 response pairs | 32,640 | 32-byte response scalars for each curve and ring branch |

There is no serialized private scalar, BIP-39 phrase, ECDSA nonce, certificate
private-key field, or server memory value.

## Construction and hiding argument

For a scalar `d`, the generator uses 128 base-4 digits of:

- `d`, when `d < 2^255`;
- `N_R1 - 1 - d`, when `d >= 2^255`.

For each digit `d_i`, it creates independent Pedersen commitments on both
curves:

`C1_i = r1_i H1 + d_i G1`

`C2_i = r2_i H2 + d_i G2`

The secondary points `H1` and `H2` are deterministic NUMS points obtained
from curve-specific SHA-256 tags by try-and-increment. The code does not know
their discrete logarithms relative to the standard generators. Both curves
have cofactor one.

The first 127 blinding scalars are sampled independently with
`os.urandom`; the final blinding scalar is chosen so that the weighted sum
of all 128 blindings is zero modulo the corresponding curve order. Therefore
the weighted sum of the commitments equals the corresponding public key,
while each digit remains hidden by its Pedersen blinding under the discrete
logarithm assumption.

The Borromean ring proof demonstrates, for every digit position, that the
same digit choice in the allowed range opens both curve commitments. The
challenge hashes the version, flip bit, both public keys and all commitments;
the response chain binds both curves together. The challenge is 128 bits, so
the intended soundness level is at most 128 bits.

## Explicitly revealed bit

The `flip` bit reveals whether the original scalar is at least `2^255`.
That is an intentional normalization choice, not an accidental leak.

The current `--gen` path explicitly retries until `0 < d < 2^255`, so the
committed `bounty.proof` has `flip = 0`. The bit therefore adds no
information about the current generated key beyond the already visible
generation constraint. A proof made with `--prove` for a different key may
have `flip = 1` and would reveal that one predicate.

## Verification boundaries

- `verify_xcurve` checks the proof structure, curve points, commitment sums,
  scalar ranges, Borromean ring transcript and resulting Bitcoin address.
- The `--verify` command additionally extracts the P-256 public key from the
  certificate and requires it to equal the proof's Q1.
- `audit/check_public_proof.py` verifies the committed proof offline and
  checks its derived address and exact length. It does not fetch or parse the
  TLS certificate; therefore it verifies the public cross-curve relation, not
  the certificate-to-Q1 binding.
- The new `audit/test_public_proof.py` exercises synthetic low/high scalars,
  both flip paths, corrupted-proof rejection and mismatched-certificate-key
  rejection without writing keys or artifacts.

The proof is not generated by the server and does not expose a transcript
correlated with the server's TLS ECDSA nonces. Its soundness and hiding rely on
the elliptic-curve discrete-log assumptions, correct random sampling and the
hash-based Fiat-Shamir/Borromean construction.

The public proof verifier already passed in bounded-audit run
https://github.com/miSultanato/k15/actions/runs/45460761523.

The synthetic generator regression has been added to the bounded-audit
workflow and awaits its first run. Until that passes, the source-level review
and existing offline verifier are evidence, but the new regression is not
yet validated in CI.

**Assessment:** no direct private-scalar disclosure is apparent in the public
proof format or generator. The only intentional scalar predicate is the
`flip` bit described above; it is zero for the committed generated proof.
This is a bounded design review, not a formal proof of zero knowledge or a
cryptanalytic security reduction.
